### 10. Shepherd + babysit

The controller owns the loop. A fresh pr-shepherd handles one prepared wave and stops; it never polls CI or waits for more findings. Use native APIs unless the adapter confirms the optional helper protocol.

#### 10a. Controller-driven (default)
1. Wait for current-head CI/review evidence using native APIs. For a configured marker-compatible bot, run review-wait with AI_REVIEW_BOT and a bounded timeout. ci-wait alone proves check status, not a reviewer's approval. **One message per wait:** run `review-wait` / `ci-wait` as a background Bash task and end the turn; its exit re-invokes the controller. **Arm `~/.claude/bin/thread-watch <pr>...` in the background on every open PR in the set, at PR open and again after each wave push** (one watcher can take several PRs): it exits on an unresolved thread from ANY reviewer (e.g. a Codex connector), not just AI_REVIEW_BOT, and on CONFLICTING, which `review-wait` never sees after a verdict or for a stacked PR. Handle `review-wait` exit 4 (`THREADS head=… authors=…`, threads before the bot decided) like a finished review: build the wave from `pr-threads --reviews`. **An approval does not end the review.** `REVIEW DONE … approval=approved unresolved_threads=N` with N > 0, or an APPROVED PR that still shows open threads, goes to step 2 like any other review: reviewers approve while leaving threads they call non-blocking, warnings or nits, and a base branch that requires conversation resolution will not merge until each is resolved. Keep `thread-watch` armed after approval until the PR merges. Keep the ~30-minute ScheduleWakeup heartbeat from the global long-running-agent rules as the fallback. Never poll status in a loop — every check re-reads the whole controller context (measured: ~240k tokens per message, 200 messages across five runs' Phase 10), and the bot and CI take minutes regardless.
2. Run pr-threads <pr> --reviews from the worktree into the wave file. Include review-body findings and relevant failed-check evidence. Missing/empty reports are failures, not zero findings.
3. Triage each item under the Finding contract against anchored code (targeted line ranges, or delegate; SKILL.md § Controller discipline). Append dispositions and evidence to the ledger, one entry per thread with `pr`, `thread` and the thread author in `reviewer_ids` (`reference/review-policy.md` § Record value). Size skips/refusals block completion even with zero findings. Every open thread is an item, from any reviewer and with any label, the "non-blocking" ones on an approved review included. Each gets one of two dispositions:
   - **Real issue** — a concrete failure scenario that normal use of the shipped code reaches (BLOCKER/MAJOR) → FIX.
   - **Real but a corner case** — the scenario exists but needs an unusual setup, is already recoverable or caught elsewhere, or the fix costs more than the risk (MINOR) → REPLY-CLOSE: a reply that names the scenario and why it is skipped, then resolve.
   A thread the reviewer labelled a nit (`ai-review:sev=nit`) starts as REPLY-CLOSE. It moves to FIX only when the ledger entry names its reach path: the `file:line` where a normal-use request enters the failing code on this head (SKILL.md § Finding contract). Record the reviewer's label and the reach path, or "none", in the ledger for every nit.
   A REPLY-CLOSE whose rationale is that no rule or policy requires the change needs the rules search in `premise_evidence` (`reference/review-policy.md` § Record value); a hit moves it to FIX or to the owner.
   No thread stays open without an owner-resolution reason (step 6).
4. Dispatch fresh pr-shepherd with worktree, PR, standing decisions, Finding contract, wave file and FIX/REPLY-CLOSE lists. Model per SKILL.md § Model matrix: `opus` at `high`. Dispatch on `fable` only when the wave holds a thread reopened after an earlier fix, or a finding the previous fixer disputed and the reviewer upheld, and say so in the brief with `Escalated after: <wave and thread>` (`effort-guard` denies a `fable` fixer without it). No-fable mode stays on `opus`. FIX means accepted BLOCKER/MAJOR: scoped verification and commits. MINOR gets a rationale reply and close where the review policy allows it.
5. Verify its report, pushed head and confirmed thread states. Append the updated ledger record for every thread the wave replied to (fixed, reply-closed with no edit, nits included, or parked) with `resolution_ref` (the fixing SHA, or `reply`) and `status`; Phase 11 counts threads from these records. If the adapter requires post-close audits, trigger the configured review when no push did so, then use audit-wait. Do not assume a close starts an audit.
6. Reopened/parked threads need owner resolution; never repeat the same close disposition. Regenerate handover state from GitHub. Repeat only for new actionable findings.

Done requires all required checks/approvals for the current head, zero unresolved threads from any reviewer (an approval or a "non-blocking" label never exempts one), zero material findings, and no pending required audit. No broad exclusion of human review gates.

#### 10b. Optional Workflow loop
Use shepherd-waves.js only with a compatible Workflow runtime and the configured marker-compatible bot. Confirm explicit opt-in required by the runtime. It applies the same triage, wave and audit contracts with a bounded wave limit. Pass the model-matrix effort explicitly in the args (`fixEffort: 'high'`, `classifyEffort: 'medium'`) alongside `fixModel`; the two are separate so a model change never changes effort. `fixModel` defaults to `opus` and applies to every wave of the loop. The script does not escalate: a loop that ends with reopened threads hands back to 10a, where the escalated wave runs on `fable`.
Before resuming, verify no live writer owns the worktree and inspect worktree state; the script cannot establish this itself. Restart the runtime after installing a new agent definition.

#### Liveness and limits
- Dispatch the first fixer after the first actionable wave exists. The controller owns waiting before that point.
- Confirm any prior fixer is stopped before dispatch; never test/build concurrently with a writer in the same worktree.
- Use native status/results and bounded watchdogs. Quiet output alone does not establish liveness.
- Keep blocking operations within 300 seconds; longer work uses bounded asynchronous continuation.
- Before each push remeasure the size budget: 2,700 changed lines as GitHub counts them (additions + deletions, `.md` review reports included), 75 files, 200 KB, base-relative. Review waves grow a PR, so a PR opened near the cap crosses it here. An unapproved over-budget wave commits locally, reports BLOCKED: size, and waits for the controller to obtain user approval.
- Resolve routine questions through standing decisions or expert consultation; only critical non-resolvable decisions go to the user.

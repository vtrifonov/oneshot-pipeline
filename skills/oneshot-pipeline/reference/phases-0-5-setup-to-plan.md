### 0. Setup (before ANY work — including the brainstorm)
- On a new installation, read `reference/distribution.md` and verify required support and external capabilities before creating the worktree.
- Read `reference/repository-adapter.md`; resolve repository/runtime settings and durable artifact directory.
- `git fetch --prune`.
- Create a **new worktree** and task branch off the adapter's latest remote base. Resolve the worktree location and branch name from the target repository; otherwise use a sibling worktree named for the task. In a multi-PR run (SKILL.md § Multi-PR runs), this is the first PR's worktree; each later PR gets its own worktree in its repository when its Phase 6 starts.
- ALL pipeline work — spec, plan, code, panel/review runs — happens inside that worktree, never in the main checkout.
- Confirm no other live agent owns this worktree using native agent status and worktree state. One implementation writer per worktree. Parallel reviewers may write only their separately assigned findings files. **Each design artifact has exactly one writer agent:** the `opus` spec agent owns the spec file (Phases 2–3), the `fable` plan agent owns the plan file (Phases 4–5). The controller alone edits the review ledger and metrics, and no implementer runs while a spec or plan agent is out.
- **Run options (last step, before the brainstorm dispatch).** For each of mode (`standard`/`quick`), model set (`fable`/`no-fable`) and brainstorm (`full`/`skip`) the invocation did not name, pre-triage the raw request against the lane trigger categories (→ mode), run `scripts/usage-budget.py` (→ model set, 20%-of-weekly-limit-per-working-day pace), and read the ticket in full (→ brainstorm: SKILL.md § Run options rule 3 — concrete behaviour, done-when, out-of-scope, no open choice), then ask in ONE `AskUserQuestion` call. One question per unnamed option: mode first ("Quick mode?"), then model set ("Use fable?"), then brainstorm ("Run the brainstorm?"). In each, the recommended choice goes first, labelled "(Recommended)", and every description gives a reason specific to this request. The budget numbers go in the fable question's text; what the ticket has or lacks goes in the brainstorm question's text. Recommendation rules and the "you pick" / unattended path are in SKILL.md § Run options. Skip the model question when `fable` is unavailable. **Frontend design** is the conditional third question: when `frontend-design:frontend-design` is available, the pre-triage sees a UI change and the invocation did not name it, resolve the target's `owner/name` and run `python3 <skill-dir>/scripts/repo-prefs.py get <owner/name> frontend_design`. On `unset`, add "Use frontend-design for the UI?" to the same call (`Use it` / `Skip this run` / `Always for this repo` / `Never for this repo`, recommendation first). On `always` or `never`, apply it with source `repo-pref` and do not ask. After the answer, persist `Always`/`Never` with `repo-prefs.py set`. The full rules are in SKILL.md § Frontend design. Record `mode=`, `models=`, `brainstorm=`, `frontend_design=` and each option's source (`named`/`asked`/`recommended`/`repo-pref`) in `/tmp/<slug>/timeline.txt`, then dispatch the brainstorm agent on the chosen model — or, with `brainstorm=skip`, go to §1 "Skip branch".

### 1. Brainstorm (checkpoint — the ONLY planned check-in) — `fable` drafts, controller relays

**Skip branch (`brainstorm=skip`).** No design agent, no question round, no approval wait. The controller:
1. Writes `/tmp/<slug>/design-brief.md` itself: the ticket text verbatim under `## Ticket` (summary, description, acceptance, out-of-scope, linked tickets); `## Standing decisions` with the defaults — the ticket wins a spec-vs-reviewer conflict unless the reviewer shows a failure scenario the ticket did not consider; the ticket's out-of-scope list is the scope cut; naming follows the repository; a decision that changes *how* is the spec agent's call, a decision that changes *what gets built* is the Contract's critical-non-resolvable path; `## PR set` with one entry per repository the ticket touches (one PR in the current repository when it names none), each with a size estimate from a bounded `rg` recon of the touched area; `## Lane` with the provisional lane and the trigger rows it matched, from the same recon.
2. Writes `approved=ticket` (plus the UTC time) and the `pr-set:` lines to `/tmp/<slug>/timeline.txt`.
3. Posts ONE status line: lane and trigger rows, PR set, the options and their sources, and "no design round: ticket is the spec". Not a question. The only ask that survives is a PR projected over the size budget (SKILL.md Contract), and it is asked here, with the three numbers and a split.
4. Quick-mode re-discussion has no checkpoint to land on: a `named` option stays; a `recommended` option whose Phase 0 basis no longer holds (a trust-boundary, persistence, concurrency or deploy-safety trigger in the recon) is upgraded to `standard` by the controller — upgrade, never downgrade — with one line in the status message and in the PR body.
5. Frontend design discovered late (the recon shows UI the Phase 0 pre-triage missed): apply SKILL.md § Frontend design as at Phase 0 — ask only when no repo preference is stored and nothing was named; otherwise apply the preference. The spec agent then owns the `## UI design` section the design agent would have written.
Then Phase 2, with the brief addition in §2 "Ticket as the brief".

**Full branch (`brainstorm=full`)** follows below.
- Dispatch a **`fable` design agent** with the raw request, the repository adapter's domain risks, and instructions to apply `superpowers:brainstorming`. It returns: the question set (ordered, most design-determining first), the candidate approaches with trade-offs, and the open decisions it cannot resolve from the repo.
- **Frontend design on:** add to the same brief an instruction to apply `frontend-design:frontend-design` to the UI parts, with the repository's design system, component library and neighbouring screens named as the brief it must follow. Its deliverable gains a `## UI design` section: layout as ASCII wireframes, empty/error/loading states, user-facing copy, the quality floor (responsive, visible keyboard focus, reduced motion, accessible contrast), and new tokens only where the repository defines none. The UI options go to the user in the same checkpoint round as the other design questions.
- **Frontend design discovered late:** if it was never asked at Phase 0 (no UI seen) but the agreed design touches UI, check the SKILL.md § Frontend design conditions now. If they hold, ask in this checkpoint round. If the answer turns it on, `SendMessage` the same design agent to apply the skill and add the `## UI design` section before the user approves.
- **The design agent never talks to the user.** Subagents cannot reach them. The controller puts the questions to the user (one `AskUserQuestion` round where the options are genuinely distinct; plain prose otherwise), then sends the answers back to the SAME agent via `SendMessage` so it keeps its context. Iterate until design intent is clear — usually one or two rounds.
- The design agent's final deliverable is the **agreed design brief plus the standing decisions** for foreseeable decision classes (spec-vs-reviewer conflicts, scope cuts, naming), written to `/tmp/<slug>/design-brief.md`. That file is the only input the Phase 2 spec agent needs; it never re-reads the conversation.
- Keep the agent's name so Phase 2 can either continue it or seed a fresh one from `design-brief.md`. If it died with the session, seed fresh from the file — never reconstruct the design from memory.
- **PR set.** The design agent proposes the PR set (SKILL.md § Multi-PR runs): one entry per PR with repository, base, scope and `depends-on` gate. The controller puts it to the user in the same round, and the agreed set goes into `design-brief.md` and as `pr-set:` lines in `timeline.txt`. It defines what the invocation pre-approves.
- Get the user's explicit approval of the direction. After this, go autonomous.
- **Provisional lane triage is the controller's call, not the agent's** (table in SKILL.md, against the agreed design and expected files). State the lane and the matching trigger rows in one line to the user as part of the approval, `mkdir -p /tmp/<slug>`, and write `date -u +%FT%TZ` as `approved=` into `/tmp/<slug>/timeline.txt`.
- **Quick mode, if it is on (named or picked at Phase 0):** say so in the same approval line (`mode=quick`) with what it buys and drops — spec panel capped at two, no plan panel, inline TDD. If a provisional trigger is a trust boundary, persistence shape, concurrency, or a deploy-safety rule, name that trigger here and ask in this same round whether to keep quick mode; their answer is a standing decision, recorded in `design-brief.md`. **This is the only place quick mode is ever discussed** — after the checkpoint it is settled for the run.

### 2. Spec — written by an `opus` agent
- Dispatch an **`opus` spec agent** whose brief is: `/tmp/<slug>/design-brief.md`, the standing decisions, the worktree path, the target path under `docs/superpowers/specs/`, and the repository adapter's spec conventions. **It writes the file itself** — the controller does not transcribe it.
- **Ticket as the brief (`brainstorm=skip`):** the design brief is the ticket, so the spec agent is also the first reader to find what the ticket left unsaid. Its brief adds: write a `## Decisions beyond the ticket` section — every choice the spec makes that the ticket did not (formats, event names, which existing path is reused, ordering), one line each with the reason — and keep it at the top of the spec, because the controller copies it into the PR body and the user reads it there instead of in a question round. A decision that would change what gets built (not how) goes to the controller as a question, which takes the Contract's critical-non-resolvable path.
- **The brief claims the spec file with `Sole writer: <absolute spec path>`** (SKILL.md § Sole writer). A requirement the user adds while the spec agent runs is held as a `pending-change:` line in the timeline and dispatched as a fresh revision after the agent reports, never sent to the running agent alongside a reviser.
- The brief carries SKILL.md § Brief discipline, the same read discipline as a panel brief (headings first, scoped `offset`/`limit` reads of any doc over ~600 lines) and the same command rules as any dispatch: no multi-line bash, no `&&`, no destructive commands. Arm a stall watchdog in the same turn as the dispatch.
- **Frontend design on:** the spec carries the design brief's `## UI design` section as its own section, unchanged in substance. Spec reviewers treat it as requirements: a missing UI state or a broken quality-floor item is a finding like any other.
- Before finalizing the testing section, inspect coupled source/test surfaces using the adapter's available checks and repository documentation.
- When the agent signals done, the **controller confirms the lane** against it (second column of the table) from the spec's headings and targeted `rg` hits for the trigger categories, not a whole-file Read; a new match upgrades. Lite lane: spec and task list in the same document; Phases 3–5 collapse to one panel run on it. The `opus` spec agent writes the spec sections and stops; the `fable` plan agent then appends the task list to that same file. Sequential handoff — the two never hold the file at once, and each is still the sole author of its own sections for revisions.

### 3. Expert panel on spec
- **Quick mode caps this panel at TWO reviewers, whatever the lane and risk selection would have chosen.** Pick the two widest-coverage scopes — requirements/architecture, plus the single highest-risk domain named by triage — and brief them that they are the only pass the design gets, because Phase 5 will not run. Everything else in this phase (findings files, ledger, dispositions, rewrites by the `opus` spec agent, targeted rechecks) is unchanged; the cap is on reviewer count, not on rigor. Dropped scopes are named in the ledger as `not-covered (quick)` so Phase 7 knows where to look hardest.
- Read `reference/review-policy.md`. Lite: one combined spec/task reviewer. Ordinary full: two independent spec reviewers (requirements/architecture + relevant domain). High risk: three–four distinct scopes; fifth only for a named uncovered risk. Use available concurrency, same artifact revision, minimal scoped context, findings files, and no peer findings before submission.
- Spec reviewers assess intent, boundaries, invariants, failure behavior, compatibility, and scope. Answer applicable repository-adapter domain questions with evidence; mark irrelevant ones N/A with a reason. No finding quota.
- **Long reference docs are read by section.** List headings first, then read only relevant sections for the changed surfaces; do not repeatedly load whole documents.
- Controller validates premises and anchors, deduplicates into the review ledger, and records accepted/rejected/duplicate/unresolved dispositions. Park MINOR per contract, and request targeted delta rechecks. Resolve design decisions against standing decisions; escalate only critical non-resolvable decisions. Record unique accepted phase B/M/m and per-reviewer pass metrics per review policy.
- **Spec rewrites go back to the `opus` spec agent, never to the controller's editor.** Send it the accepted BLOCKER/MAJOR dispositions — the claim, the failure scenario, the fix sketch, and the controller's ruling — and let it rewrite the affected sections. Dispatch a fresh `opus` author per round, seeded as `reference/review-policy.md` step 4 says (never `SendMessage` the old one). The controller triages and verifies the rewrite landed; it does not author spec prose.

### 4. Plan — written by a `fable` agent
- **Quick mode does not skip this phase.** The plan is written exactly as below and matters *more*, not less: with no Phase 5 panel and no SDD reviewer, the requirement → task → verification matrix and the invariant/edge-case list are the only written statement of what the inline TDD implementation must prove. Brief the plan agent that each task must name the assertion its test will make, or say in one line why the task has no assertable behavior.
- Dispatch a **`fable` plan agent** from the reviewed spec, briefed to apply `superpowers:writing-plans`. It writes the plan file itself, under the adapter's plans path, and is the sole writer of that file (`Sole writer: <absolute plan path>` in the brief). Same dispatch discipline as the spec agent: scoped reads, no multi-line bash, no `&&`, no destructive commands, stall watchdog armed in the same turn.
- **Complexity flags are justified.** The plan author marks a task "complex" only with a one-line named risk (cross-package contract, concurrency, security boundary, ...). Expect ≤ ~20% of tasks flagged; above that the controller challenges the flags (a `rg` count over the plan, not a Read) and sends the excess back before Phase 6 dispatch. An unjustified flag means the task runs on `sonnet`; flagged tasks get `opus` implementers and make their batch's reviewer `opus` (SKILL.md § Model matrix).
- Include a compact requirement → task → verification matrix. The plan must carry the panel's surface enumeration as explicit tasks (one task per coupled surface), and the invariant/edge-case matrix as the TDD test list for any stateful mechanism — designing these live inside PR review cost ~6 cycles each on three separate PRs.
- **Frontend design on:** each UI task copies the parts of the spec's UI design section it implements (wireframe, states, copy) and the quality floor into its own text, because implementers never read the spec. A UI task with assertable behavior (a state renders, focus moves, copy appears) names that assertion like any other task.
- **Docs PR first when the code is near the cap.** The plan projects each PR's size as GitHub counts it (additions + deletions, `.md` included). When a code PR would land within ~500 lines of the 2,700 cap, the PR set's part 1 is spec + plan + ledger + archive row (docs only, exempt from the line cap), opened before any code part, and the code parts follow at ≤ 2,700 each. Measured cost of skipping this: one run lost 1h35 in Phase 10 because 1,200 `.md` lines pushed a 2,300-line code PR past the bot's auto-approval limit.
- **Plan size cap: under 2,000 lines.** The Read tool returns 2,000 lines by default, so a longer plan is silently truncated for every panel lens and every reader that opens it whole (measured plans of 100–275k chars). Past the cap, split into `<plan>-part-N.md` files by task group and link them from a short index plan.

### 5. Expert panel on plan
- **Skipped entirely in quick mode** — no reviewer, no ledger entries, no rechecks; go straight from the written plan to Phase 6 inline TDD. Record `plan_bmm=skipped(quick)` in the metrics row so a retro can tell a skipped panel from a clean one. A finding that would have landed here surfaces instead as a failing RED test in Phase 6 or in the Phase 7 code review; when it does, note it in the run summary — that is the evidence the retro needs to judge whether quick mode pays.
- Full lane only. Apply the plan contract in `reference/review-policy.md`: one fresh implementation/test reviewer for ordinary full, two for high risk. Verify task coverage, ordering, integration, and applicable migration/rollout/rollback; reopen design only with new failure evidence. Same ledger and per-pass recording; targeted rechecks rather than repeating the spec panel.
- **Plan revisions go back to the `fable` plan agent**, same protocol as the spec: controller triages and rules, the plan agent rewrites the affected tasks. A fresh `fable` author per round, seeded per `reference/review-policy.md` step 4. A finding that reopens the design amends the spec first (back to the `opus` spec agent), then the plan follows — never the plan alone.

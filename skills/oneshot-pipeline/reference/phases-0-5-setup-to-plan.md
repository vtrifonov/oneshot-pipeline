### 0. Setup (before ANY work — including the brainstorm)
- On a new installation, read `reference/distribution.md` and verify required support and external capabilities before creating the worktree.
- Read `reference/repository-adapter.md`; resolve repository/runtime settings and durable artifact directory.
- `git fetch --prune`.
- Create a **new worktree** and task branch off the adapter's latest remote base. Resolve the worktree location and branch name from the target repository; otherwise use a sibling worktree named for the task.
- ALL pipeline work — spec, plan, code, panel/review runs — happens inside that worktree, never in the main checkout.
- Confirm no other live agent owns this worktree using native agent status and worktree state. One implementation writer per worktree. Parallel reviewers may write only their separately assigned findings files. **Each design artifact has exactly one writer agent:** the `opus` spec agent owns the spec file (Phases 2–3), the `fable` plan agent owns the plan file (Phases 4–5). The controller alone edits the review ledger and metrics, and no implementer runs while a spec or plan agent is out.
- **Run options (last step, before the brainstorm dispatch).** For each of mode (`standard`/`quick`) and model set (`fable`/`no-fable`) the invocation did not name, pre-triage the raw request against the lane trigger categories (→ mode) and run `scripts/usage-budget.py` (→ model set, 20%-of-weekly-limit-per-working-day pace), then ask in ONE `AskUserQuestion` call. One question per unnamed option: mode first ("Quick mode?"), then model set ("Use fable?"). In each, the recommended choice goes first, labelled "(Recommended)", and every description gives a reason specific to this request. The budget numbers go in the fable question's text. Recommendation rules and the "you pick" / unattended path are in SKILL.md § Run options. Skip the model question when `fable` is unavailable. Record `mode=`, `models=` and each option's source (`named`/`asked`/`recommended`) in `/tmp/<slug>/timeline.txt`, then dispatch the brainstorm agent on the chosen model.

### 1. Brainstorm (checkpoint — the ONLY planned check-in) — `fable` drafts, controller relays
- Dispatch a **`fable` design agent** with the raw request, the repository adapter's domain risks, and instructions to apply `superpowers:brainstorming`. It returns: the question set (ordered, most design-determining first), the candidate approaches with trade-offs, and the open decisions it cannot resolve from the repo.
- **The design agent never talks to the user.** Subagents cannot reach them. The controller puts the questions to the user (one `AskUserQuestion` round where the options are genuinely distinct; plain prose otherwise), then sends the answers back to the SAME agent via `SendMessage` so it keeps its context. Iterate until design intent is clear — usually one or two rounds.
- The design agent's final deliverable is the **agreed design brief plus the standing decisions** for foreseeable decision classes (spec-vs-reviewer conflicts, scope cuts, naming), written to `/tmp/<slug>/design-brief.md`. That file is the only input the Phase 2 spec agent needs; it never re-reads the conversation.
- Keep the agent's name so Phase 2 can either continue it or seed a fresh one from `design-brief.md`. If it died with the session, seed fresh from the file — never reconstruct the design from memory.
- Get the user's explicit approval of the direction. After this, go autonomous.
- **Provisional lane triage is the controller's call, not the agent's** (table in SKILL.md, against the agreed design and expected files). State the lane and the matching trigger rows in one line to the user as part of the approval, `mkdir -p /tmp/<slug>`, and write `date -u +%FT%TZ` as `approved=` into `/tmp/<slug>/timeline.txt`.
- **Quick mode, if it is on (named or picked at Phase 0):** say so in the same approval line (`mode=quick`) with what it buys and drops — spec panel capped at two, no plan panel, inline TDD. If a provisional trigger is a trust boundary, persistence shape, concurrency, or a deploy-safety rule, name that trigger here and ask in this same round whether to keep quick mode; their answer is a standing decision, recorded in `design-brief.md`. **This is the only place quick mode is ever discussed** — after the checkpoint it is settled for the run.

### 2. Spec — written by an `opus` agent
- Dispatch an **`opus` spec agent** whose brief is: `/tmp/<slug>/design-brief.md`, the standing decisions, the worktree path, the target path under `docs/superpowers/specs/`, and the repository adapter's spec conventions. **It writes the file itself** — the controller does not transcribe it.
- The brief carries the same read discipline as a panel brief (headings first, scoped `offset`/`limit` reads of any doc over ~600 lines) and the same command rules as any dispatch: no multi-line bash, no `&&`, no destructive commands. Arm a stall watchdog in the same turn as the dispatch.
- Before finalizing the testing section, inspect coupled source/test surfaces using the adapter's available checks and repository documentation.
- When the agent signals done, the **controller reads the spec and confirms the lane** against it (second column of the table); a new match upgrades. Lite lane: spec and task list in the same document; Phases 3–5 collapse to one panel run on it. The `opus` spec agent writes the spec sections and stops; the `fable` plan agent then appends the task list to that same file. Sequential handoff — the two never hold the file at once, and each is still the sole author of its own sections for revisions.

### 3. Expert panel on spec
- **Quick mode caps this panel at TWO reviewers, whatever the lane and risk selection would have chosen.** Pick the two widest-coverage scopes — requirements/architecture, plus the single highest-risk domain named by triage — and brief them that they are the only pass the design gets, because Phase 5 will not run. Everything else in this phase (findings files, ledger, dispositions, rewrites by the `opus` spec agent, targeted rechecks) is unchanged; the cap is on reviewer count, not on rigor. Dropped scopes are named in the ledger as `not-covered (quick)` so Phase 7 knows where to look hardest.
- Read `reference/review-policy.md`. Lite: one combined spec/task reviewer. Ordinary full: two independent spec reviewers (requirements/architecture + relevant domain). High risk: three–four distinct scopes; fifth only for a named uncovered risk. Use available concurrency, same artifact revision, minimal scoped context, findings files, and no peer findings before submission.
- Spec reviewers assess intent, boundaries, invariants, failure behavior, compatibility, and scope. Answer applicable repository-adapter domain questions with evidence; mark irrelevant ones N/A with a reason. No finding quota.
- **Long reference docs are read by section.** List headings first, then read only relevant sections for the changed surfaces; do not repeatedly load whole documents.
- Controller validates premises and anchors, deduplicates into the review ledger, and records accepted/rejected/duplicate/unresolved dispositions. Park MINOR per contract, and request targeted delta rechecks. Resolve design decisions against standing decisions; escalate only critical non-resolvable decisions. Record unique accepted phase B/M/m and per-reviewer pass metrics per review policy.
- **Spec rewrites go back to the `opus` spec agent, never to the controller's editor.** Send it the accepted BLOCKER/MAJOR dispositions — the claim, the failure scenario, the fix sketch, and the controller's ruling — and let it rewrite the affected sections. Continue the original agent when it is alive (`SendMessage`, keeps context); otherwise dispatch a fresh `opus` agent seeded with the spec path and the accepted-findings list. The controller triages and verifies the rewrite landed; it does not author spec prose.

### 4. Plan — written by a `fable` agent
- **Quick mode does not skip this phase.** The plan is written exactly as below and matters *more*, not less: with no Phase 5 panel and no SDD reviewer, the requirement → task → verification matrix and the invariant/edge-case list are the only written statement of what the inline TDD implementation must prove. Brief the plan agent that each task must name the assertion its test will make, or say in one line why the task has no assertable behavior.
- Dispatch a **`fable` plan agent** from the reviewed spec, briefed to apply `superpowers:writing-plans`. It writes the plan file itself, under the adapter's plans path, and is the sole writer of that file. Same dispatch discipline as the spec agent: scoped reads, no multi-line bash, no `&&`, no destructive commands, stall watchdog armed in the same turn.
- Include a compact requirement → task → verification matrix. The plan must carry the panel's surface enumeration as explicit tasks (one task per coupled surface), and the invariant/edge-case matrix as the TDD test list for any stateful mechanism — designing these live inside PR review cost ~6 cycles each on three separate PRs.
- **Plan size cap: under 2,000 lines.** The Read tool returns 2,000 lines by default, so a longer plan is silently truncated for every panel lens and every reader that opens it whole (measured plans of 100–275k chars). Past the cap, split into `<plan>-part-N.md` files by task group and link them from a short index plan.

### 5. Expert panel on plan
- **Skipped entirely in quick mode** — no reviewer, no ledger entries, no rechecks; go straight from the written plan to Phase 6 inline TDD. Record `plan_bmm=skipped(quick)` in the metrics row so a retro can tell a skipped panel from a clean one. A finding that would have landed here surfaces instead as a failing RED test in Phase 6 or in the Phase 7 code review; when it does, note it in the run summary — that is the evidence the retro needs to judge whether quick mode pays.
- Full lane only. Apply the plan contract in `reference/review-policy.md`: one fresh implementation/test reviewer for ordinary full, two for high risk. Verify task coverage, ordering, integration, and applicable migration/rollout/rollback; reopen design only with new failure evidence. Same ledger and per-pass recording; targeted rechecks rather than repeating the spec panel.
- **Plan revisions go back to the `fable` plan agent**, same protocol as the spec: controller triages and rules, the plan agent rewrites the affected tasks. Continue the original agent when alive, otherwise a fresh `fable` agent seeded with the plan path and the accepted-findings list. A finding that reopens the design amends the spec first (back to the `opus` spec agent), then the plan follows — never the plan alone.

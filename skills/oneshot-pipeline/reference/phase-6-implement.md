### 6. Implement
- Record `impl_mode` for the metrics row: `sdd` (default), `inline`, or `inline-tdd` (quick mode, §6c).
- **Quick mode goes straight to §6c** — in quick mode there is nothing to dispatch, and the eligibility test in the next bullet does not apply.
- **Inline is allowed only when BOTH hold: the confirmed lane is lite AND the expected diff is one or two files under ~100 lines.** There the two dispatch baselines (implementer + reviewer, ~55k tokens each before either reads a line) cost more than the work. Inline still gets a code review in a fresh `opus` subagent (Phase 7) — never self-review — and the controller runs `/compact` right after Phase 7 so the implementation's tool output does not ride along for the rest of the session. Anything larger is SDD: implementation output then lands in a throwaway Sonnet context instead of the controller's, which is already at 200k+ and several times the per-token price (measured 2026-09-11).
- **6a. SDD** — `superpowers:subagent-driven-development`, with the per-dispatch and watchdog rules below.
- **The brief is the task source; the plan file is not.** Every implementer and task-reviewer brief carries the full task text verbatim plus any plan section the task references (shared context, file structure, invariants). The brief says explicitly: "Do not Read the plan or the spec; everything you need is below. If a named section is missing, report BLOCKED." Never dispatch with "implement Task N from the plan at <path>" — that shape (129 dispatches in two weeks) made each implementer Read a 50–60k-char plan, ~14k tokens of context per dispatch, before writing a line. Reviewers of a batch get the spec sections for the batch's requirements the same way.
- **Start every SDD prompt with a progress tag** — `(Task 4 of 24) You are the implementer…`, `(Tasks 4–7 of 24) You are the task reviewer…`, fix rounds `(Task 4 of 24, fix 2)`. The agent list shows only the prompt's first characters, so the tag is how the user sees progress at a glance. M is the plan's total task count; keep it fixed for the run unless the plan is amended.
- Per-dispatch rules for every subagent: **no multi-line bash and no `&&` chains**; **no `rm` or any destructive command** (`mv -f`, `git clean`, `git checkout --`) — tell them to report it and let the controller delete; minimal comments; at most 5 minutes per blocking command/wait; bounded task time-box, report BLOCKED instead of spinning; file as deliverable.
  - The shared mechanism behind all of these is *an unanswerable permission prompt*: the subagent cannot approve it, so it hangs forever with no error and no notification. Anything requiring approval must never appear in a subagent's command set. Stale `tsconfig.tsbuildinfo` is the usual temptation — say explicitly that it is not theirs to clear.
  - Diagnosing: in the agent's `subagents/agent-*.jsonl`, a final `tool_use` entry with **no result after it** is the permission-prompt signature, distinct from a crash.
- Test cadence: scoped changed/co-located/importing tests per step; review batches of 3–5 tasks at a seam. The controller runs the full local suite/build in Phase 8, not every five tasks. After a gate failure, run focused diagnostics; repeat a full gate only when fixes or unresolved evidence warrant it.
- **Scoped verification once per completed step.** For compatible TypeScript/JavaScript repositories use ~/.claude/bin/verify-diff (owning tsc scopes, eslint, affected vitest tests). Other toolchains use scoped adapter gates. Do not run a full suite after every edit.
- **Review cadence: batch the SDD task reviews.** Never dispatch the task reviewer after every plan task. Review in batches of 3–5 tasks — controller picks the boundary at a natural seam (a completed module, a migration + its consumers) — plus one final pass over anything not yet reviewed. **The batch is bounded by diff size, not task count:** split when the batch crosses ~400 changed source lines or ~8–10 files, even at two tasks — past that a single reviewer skims and misses the cross-file issues that justify batching. A small batch is not waste; it is one dispatch either way. Per-task review was judged not worth its latency and token cost (the user, 2026-09-04).
- **Never end a turn on "next up: Task N".** Announcing the next task is not starting it — make the `Agent` call and arm its watchdog in the SAME turn as the report on the previous task. A turn ending in an intention leaves the pipeline stopped while looking finished, and the user burns a prompt discovering it.
- Watchdog baseline: floor "idle" at the watchdog's own start time, not the newest file mtime in the worktree — a freshly dispatched agent has written nothing yet, so an unfloored stall arm fires instantly on a healthy agent.
- **Arm a STALL watchdog on every dispatch, not a success watcher.** A watcher that fires only on "commit landed / report written" is *silent through a dead agent*, and that silence is indistinguishable from work in progress. The stall arm fires on quiet: no file write anywhere in the worktree for ~6 min while still uncommitted. Start it in the same turn as the `Agent` call.
  - Poll shape: newest mtime of `fd -t f -H -E .git -E node_modules . <worktree> --exec stat -f '%m'` **plus the agent's own `subagents/agent-*.jsonl` transcript**, vs `date +%s`; emit `STALL` past the threshold, re-arm if it resumes, exit on commit-or-report.
  - **zsh does not glob-expand unquoted variable contents.** `G="…/agent-*.jsonl"; stat -f '%m' $G` fails silently in zsh (works in bash), so a transcript-liveness check written that way is INERT — `idle` then counts from watchdog start and fires a guaranteed false STALL at the threshold on a perfectly healthy agent. In an inline Monitor command (zsh), resolve the file first: `f=$(ls -t …/agent-*.jsonl | head -1)` then `stat -f '%m' "$f"`. Or use `${~G}`. A `#!/bin/bash` script file is unaffected.
  - **Match the completion signal to the task shape.** "First commit ≠ base" is right for a single-commit task but fires on commit 1 of a multi-commit fix round; for those, wait on the REPORT FILE only and keep the stall arm. A watchdog that exits early leaves the agent unwatched for the rest of its work.
  - **The transcript is the real liveness signal** — it advances on every tool call. Worktree writes alone are not: an implementer legitimately reads for many minutes while researching, and watching writes only produces false STALLs on healthy agents. Floor the reference at the watchdog's own start time too.
  - On a STALL event: read `~/.claude/projects/<proj>/<session>/subagents/agent-*.jsonl` (largest timestamp gap = the stuck tool call), `TaskStop` the agent, then finish the work yourself or re-dispatch — never wait longer.
  - An idle notification means "finished a turn", NOT "alive" or "done". Never infer health from it, and never infer death from it either — check mtimes + transcript.

- **6b. Workflow (deterministic loop) — NOT YET AVAILABLE for implementation.** The deterministic-loop trial runs in Phase 10 only (`shepherd-waves.js`, a committed and reviewed script). Implementation gets the same treatment once a reviewed `implement-tasks.js` exists (sequential tasks, one writer per worktree; implementer → verifier → fixer per task; ≤ 4 tasks so three agents per task stay under the ~15-agent guideline). Until then use 6a; never hand-author an orchestration script mid-run — a script bug in Phase 6 costs the whole implementation, and the argument for the trial (hand-rolled orchestration was the failure class) argues against writing one per run.

- **6c. Quick-mode inline TDD (`impl_mode=inline-tdd`).** Quick mode replaces the SDD default: the controller implements in-session under `superpowers:test-driven-development`, one plan task at a time. Per task: write the test FIRST, run it, **read the failure message and confirm it fails for the intended reason** (a test that fails on an import error or a typo proves nothing), implement the smallest change that passes it, run `~/.claude/bin/verify-diff` once for the step, commit. Then the next task, same turn — the "never end a turn on an intention" rule applies to inline work too.
  - **Code-first forfeits the trade.** The failing test is what quick mode gives back for the panel it skipped at Phase 5 and the task reviewer it skipped at 6a. Writing the implementation and back-filling a test leaves the run with neither.
  - A plan task with genuinely no assertable behavior (a doc edit, a constant, a config key) skips the RED step and gets one line in the PR body saying which task and why.
  - **The inline eligibility limits do not apply** — quick mode is inline by instruction, not by size. What still applies: `/compact` right after Phase 7, and never self-review (Phase 7 in a fresh `opus` subagent; the controller wrote this code).
  - **Bail-out to 6a is expected, not a failure.** Hand the remaining tasks to SDD when the diff crosses ~400 changed source lines or ~8–10 files, when a task needs a surface the controller has not read, or when context pressure starts truncating reads. Record `impl_mode=inline-tdd→sdd`, announce it in one line, and do not ask — the bail-out is pre-approved by the mode.
  - Scoped tests during the work, full suite/build at Phase 8, exactly as elsewhere. A red `verify-diff` is fixed before the next task starts, never carried.

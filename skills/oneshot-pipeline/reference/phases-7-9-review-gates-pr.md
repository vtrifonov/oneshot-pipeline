### 7. Code review
- Lite: fresh independent correctness/testing reviewer. Full: that reviewer plus a separate security/architecture reviewer for the named risks. **Both dispatch with `effort: high`** (SKILL.md § Model matrix): the one role that runs above the measured medium baseline, because a defect that escapes here costs a Phase 10 wave. Brief them with the diff, the spec's invariants and the changed file list, and the Brief-discipline range-reading rule; effort does not replace a targeted brief. Apply available review skills or brief agents directly; use the Finding contract, SKILL.md § Brief discipline and separate findings files. Both scopes run on `opus` (SKILL.md § Model matrix).
- **Full lane, small PR: one combined reviewer.** When the PR's committed source diff (the lane-triage source filter) is at most 800 changed lines and no high-risk condition from `reference/review-policy.md` holds, dispatch ONE reviewer covering both scopes instead of two: `p7 <PR> combined review`, `opus` at `high`, its brief carrying both scope checklists. Record `code_review=combined` in `timeline.txt` and the PR body. Over 800 lines, or any high-risk condition: two reviewers as above. This is a trial: the two-reviewer panel cost 4–14M tokens and 7–12 min per reviewer, and the last seven measured security/architecture passes to 2026-11-26 accepted no BLOCKER/MAJOR (0.04 accepted per million tokens over 124 passes, the lowest of any lens). The rollup tracks the combined pass as lens `code:combined`; judge it after ten combined passes on escaped defects (Phase 10 accepted BLOCKER/MAJOR on the same PR) against two-reviewer PRs of similar size, not on its own dry rate.
- **Frontend design on:** the correctness/testing reviewer also checks the UI tasks against the spec's UI design section and its quality floor. When a browser tool is available, it renders the changed screens and attaches screenshots to its findings. A taste disagreement without a concrete broken state, flow or accessibility failure is MINOR.
- Validate premises and deduplicate. Fix accepted BLOCKER/MAJOR findings, with meaningful regression tests for behavioral bugs. MINOR follows the contract.
- **Fix rounds dispatch on `sonnet` at `medium`** (SKILL.md § Model matrix), described as `p7 <PR> fix <ids>`. The accepted finding already carries the claim, the failure scenario and the fix sketch, so the fix is a scoped task. `opus` follows the implementer rule: a `Complexity risk:` line naming the risk, or `Escalated after:` naming the failed `sonnet` attempt. A recheck of the fix goes back to the `opus` reviewer at `high`.
- Fix sibling call sites and coupled surfaces sharing the same defect; centralize a shared invariant where appropriate.

### 8. Pre-push gates (mirror CI)
- Run the repository adapter's actual CI gates from the controller. Inspect CI configuration for every owning package and independent type/build/browser-test scope; do not assume a root command covers them.
- Scoped checks during implementation; full suite/build here. Run each gate once initially, rerunning only after relevant changes, failures or unresolved evidence.
- Run `~/.claude/bin/derived-check --base <base>` before the gates: lockfiles changed since base need an install, duplicate migration timestamps need a rename and a cold test stack, tracked generated files need regeneration. Then run `~/.claude/bin/text-guards --base <base> --cmd` and run every suite it lists: guards that read changed files as text (by path, or by scanning an enclosing directory) are invisible to import-graph sweeps and otherwise fail only in CI. Run its `direct` suites after every fix round too; a comment-only edit can trip them. Run cspell (and any per-package lint) from inside each package that has its own config, not only from the root.
- If the optional scoped-verification hook is registered and the repository opted in, the controller may prefix the pre-PR full run with ALLOW_FULL_SUITE=1. Subagents use scoped checks.
- **Gates run as background jobs, in parallel, and the controller waits without taking turns.** In one response, start every independent gate (build, type check, lint, each test scope) as its own background Bash job (`run_in_background`, output to `/tmp/<slug>/p8/<gate>.log`), then end the turn: each job's exit wakes the controller. No polling, no `sleep`, no reading a log before its job exits. Read a failure with `tail -n 60` of its log plus targeted `rg`, never the whole output. Mechanical fixes (formatter, lint autofix, a cspell word) run inline and rerun only that gate; anything else is a `p8 <PR> fix` round under the Phase 7 rules. The `p8-gates` start and end marks stay. Measured: one inline `p8-gates` step held the controller's ~200k context for 33 min and 18.5M tokens (2026-11-25), because every gate run and retry was a full-context turn.
- Re-evaluate all lane triggers mechanically against the committed base-relative diff. New matches upgrade the lane and add missing review coverage before push.
- Sweep applicable repository rules: source-size limits, UI accessibility, deployment path filters, access-control invariants, documentation and rollout requirements. Resolve exact rules from the target repository.
- Measure PR size on the same committed diff, the way GitHub counts it (additions + deletions, `.md` review reports, generated files and lockfiles included): git diff --shortstat <base>...HEAD and git diff <base>...HEAD | wc -c. Over 2,700 changed lines, 75 files or 200 KB without a recorded override requires user approval of the measured size and proposed split before push; the `.md`-excluded count is only a floor, never the number to report. Record size and any override in timeline.txt.
- Fix required gate failures before pushing.

### 8b. Pre-PR review (the last step before the push)
Some repositories gate merges on an AI review bot that can also run locally: the same rules and criteria, posting nothing. The adapter's `Optional pre-PR review` setting names zero or more review skills that run it. Running them here, after every Phase 7 fix and with the gates green, shows the bot's findings on the exact tree that gets pushed; each one caught saves a 25–100 min Phase 10 wave.
- **When.** Every lane and mode, per PR, after that PR's Phase 8 gates pass and before its first push. Not again in Phase 10: CI reviews every wave.
- **Invoke each skill by name** (the Skill tool), for every entry that resolves for the target repository, with the adapter's arguments: the run's worktree only, the resolved base ref, and a one-line intent from the spec. Start them concurrently: a skill that runs a background command starts first, then a skill that dispatches a reviewer agent. The skill decides how it reviews. The pipeline overrides only what follows:
  - **Its reviewer agent** is described as `p8 <PR> pre-pr-<name> review` and runs on `opus` at `high` (SKILL.md § Model matrix). It gets the skill's printed prompt **verbatim**, never a fork, never the controller's summary: the one brief exempt from SKILL.md § Finding contract and § Brief discipline.
  - **Output** goes under `/tmp/<slug>/p8-pre-pr-<name>/` (pass it as the skill's output path when it takes one; otherwise save the final report there).
  - **The skill's fix step yields to the pipeline.** Map its findings into the shared ledger with the adapter's severity mapping: the blocking level becomes a BLOCKER candidate; a warning becomes MAJOR only when the controller can state a concrete failure scenario, otherwise MINOR. Verify each premise with targeted `rg` and line ranges, deduplicate against the Phase 7 ledger and the other skills, and give every finding a disposition. Rejecting one because no rule requires it needs the rules search in `premise_evidence` (`reference/review-policy.md` § Record value). Accepted BLOCKER/MAJOR fixes dispatch as `p8 <PR> fix <ids>` under the Phase 7 fix-round rules (regression test first for a behavioural bug), and **are committed**, whatever the skill says about leaving fixes uncommitted. MINOR follows the contract and lands in the PR body's Parked list.
  - **Skip steps that have no meaning in a run**, as the adapter lists them (a receipt for a task record the run doesn't have, for example). Never post anything and never push from inside the skill.
- **One pass each.** No second run of any skill after the fixes. A BLOCKER fix gets one `opus` recheck at `high` (`p8 <PR> recheck <ids>`); the rest rely on the gates.
- **Then re-run the gates the fixes touched** and re-measure the PR size on the committed diff before Phase 9.
- **Coverage.** When a skill reports that it saw less than the whole change (scale limits, criteria dropped at a budget, untracked files), record it in timeline.txt and in the disposition.
- **Record** `pre_pr_review_<name>=done|failed(<reason>)|skipped(<reason>)` in timeline.txt. A failed or unresolved skill never blocks the push. When no skill is configured or none resolves for this repository, record `pre_pr_review=skipped(<reason>)`.

### 9. PR
- Sync with the adapter's latest remote base. Rebase before first push; after publication merge the base in when needed, never amend or force-push.
- Push and create this PR of the authorized PR set (SKILL.md § Multi-PR runs) against its resolved base. A dependent PR opens as a draft once its Phase 8 is green while its `merged`/`deployed` gate does not hold, and becomes ready for review after it does; a `published` gate still blocks the push (SKILL.md § Multi-PR runs). Body includes spec/plan links, lane and matching triggers, mode, impl_mode, validation and Parked (MINOR) rationale, and, when the set has more than one PR, its siblings with their order and gates. Record pr_open with the PR index in timeline.txt.
- Diagrams use Mermaid fences. Check the actual PR body before create/edit.
- Batch pushes, never delay triaged work: implement, test and commit each accepted fix immediately, then push one coherent wave.
- A flaky check gets a bounded rerun through rerun-failed, never a source commit to retrigger CI. Do not treat a failed rerun as success.
- Opening the PR is not completion. Verify required CI and current-head reviews before claiming merge readiness.
- A review refusal or size skip is not a clean review. Follow the configured reviewer protocol and size-override contract; do not invent a deep-review command for an unknown bot.
